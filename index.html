Step 1 — Understand Requirements

The Real Industry Problem & Requirements

Campus placement teams manage millions in offers across fragile spreadsheets and chaotic email chains. CPDMS replaces this with an authoritative, unified system of record.

⚠️

The Spreadsheet Chaos

  • ❌ Duplicate Data: Inconsistent records across 15+ Google Sheets and email inboxes.
  • ❌ Missed Deadlines: Students apply past cutoffs; admins manually filter timestamps.
  • ❌ Eligibility Errors: Students with low CGPA apply anyway, congesting interviewer schedules.
  • ❌ Opaque Outcomes: Students spam CDC offices asking for selection status updates.
🛡️

The CPDMS Engineered Solution

  • ✅ Single Source of Truth: One centralized database with referential integrity.
  • ✅ Automated Cutoffs: Server-side deadline and CGPA validation guards.
  • ✅ Zero Duplicate Policy: Unique composite constraints guarantee 1 application per drive.
  • ✅ Transparent Pipeline: Real-time status tracker (Applied → Shortlisted → Selected).

User Personas & Functional Scope

Persona 1

Placement Admin (CDC)

University director and placement coordinators.

  • Register and manage company partners.
  • Create placement drives with role, package, CGPA, and deadline.
  • Inspect and export applicant rosters.
Persona 2

Graduating Student

Final and pre-final year engineering candidates.

  • Browse active placement opportunities.
  • Receive automated eligibility feedback.
  • Submit strictly 1 application per drive.
  • Track application status in real-time.
Persona 3

Placement Team / TPO

Ground coordinators executing interview rounds.

  • Update candidate stages: Shortlisted, Selected, Rejected.
  • Broadcast schedule notifications to candidates.
  • Generate placement statistics and accreditation reports.

Non-Functional Requirements (NFR)

⚡ High Performance

Sub-150ms read latency for drive listing via Redis caching layers.

🔒 Data Integrity & ACID

PostgreSQL composite unique keys eliminate race conditions during high-volume application spikes.

📱 Responsive UI

Seamless layout on mobile screens during rapid on-campus interview rounds.

🛡️ Role-Based Access

JWT tokens with claims ensuring students cannot alter drive requirements or view others' outcomes.

Critical Failure Flows & Compensations

Payment Gateway Timeout

If the bank gateway fails to acknowledge within 30 seconds, order transitions to PAYMENT_PENDING with a 5-minute expiry countdown before auto-cancellation.

No Rider Assigned

Radius expansion algorithm increases geo-fence from 3km to 6km. If unassigned after 8 minutes, customer is prompted for cancellation with full compensation credit.

Live WebSocket Disconnect

Client automatically falls back to HTTP Long-Polling every 5 seconds to track rider GPS coordinates without breaking user UI.

Championship Technical Interview Q&A

1. Explain the difference between HLD and LLD using your project. ➕
Answer: High-Level Design (HLD) defines the broad system boundaries, macro services (Drive Service, Application Service, Notification Queue), networking protocols, and scalability strategy (PostgreSQL with Redis caching). Low-Level Design (LLD) drills into class schemas, specific REST endpoint contracts, data types, exact validation guards, and the step-by-step logic of the applyToDrive() function.
2. Why did you choose these entities for your ER Diagram? ➕
Answer: The business domain consists of four primary actors and events: COMPANY (the recruiting partner), PLACEMENT_DRIVE (the recruiting event with role and cutoffs), STUDENT (the candidate master), and APPLICATION (the transactional join entity capturing when a student applies, their eligibility snapshot, and round outcomes).
3. Explain the relationship between Placement Drive and Application. ➕
Answer: It is a 1-to-Many relationship. A single Placement Drive can receive hundreds of Applications from different candidates, but each Application belongs strictly to one Placement Drive. Across Student and Placement Drive, Application functions as the associative bridge entity for a Many-to-Many relationship.
4. How would you prevent duplicate applications? ➕
Answer: We enforce duplicate prevention across three layers: 1. UI Layer: Disable the "Apply" button and show "Already Applied" if the student's ID is in the drive's applicant roster.
2. Application Service Layer: Check applicationAlreadyExists(studentId, driveId) before executing write queries.
3. Database Layer (Authoritative): A composite unique constraint UNIQUE (student_id, drive_id) in PostgreSQL guarantees zero duplicate entries even under concurrent race conditions.
5. What validation should happen on frontend vs backend? ➕
Answer: • Frontend Validation: Fast user feedback for field formats (non-empty role, positive package, date picker min date set to tomorrow). Never trusted for security.
• Backend Validation: Mandatory authoritative checks. Validating student identity via JWT claims, fetching authoritative CGPA from the master database, and checking current server time against the drive deadline.
6. How would your architecture change if 100,000 students used the system? ➕
Answer: 1. Introduce an Application Load Balancer (ALB) distributing traffic across autoscaled stateless container nodes.
2. Deploy a Redis Cache Cluster to cache public active drives, absorbing 95% of read queries.
3. Separate PostgreSQL into Primary (Writes) and Read Replicas (Listing Queries).
4. Transition application submission to an asynchronous message queue (Apache Kafka) with worker consumers processing writes smoothly without overloading the database.
7. Describe one important error flow in your design. ➕
Answer: When a student attempts to apply after the deadline has passed. The Application Service checks CURRENT_TIMESTAMP > drive.deadline, rejects the submission with HTTP 400 Bad Request ("Application deadline has passed"), logs the rejected attempt to audit storage, and returns an actionable error message to the student UI.
8. Walk me through your design from business requirement to database. ➕
Answer: The requirement "Students can submit one application per drive" translates into: 1. UI: Drive card with live CGPA eligibility badge and single-click Apply modal.
2. API: POST /applications receiving {studentId, driveId}.
3. Service: Business logic validating student existence, deadline, CGPA criteria, and duplication.
4. Database: An APPLICATION record inserted with composite index guarantee and timestamp.
